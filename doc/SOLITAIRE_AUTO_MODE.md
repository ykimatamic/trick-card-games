# オートモード仕様

本ドキュメントは、ソリティアアプリのオートモード(自動プレイ)の現行仕様を記述する。
対象コミット時点の実装: `src/engine.ts`(AIロジック)、`src/Board.tsx`(UI制御)、`src/game.ts`(ルール層)。

## 1. 概要

オートモードは「**完全探索ソルバー → プラン再生 → 簡易AIフォールバック**」の3段構成。

1. ユーザーが「▶ 自動」を押すと、現在の盤面から**解が存在するかどうかを完全探索で解析**する。
2. 解が見つかれば、手順(プラン)を実際のゲーム操作列に展開し**高速リプレイ**する。
3. 解析がノード数上限に達した場合(難敵)、**簡易AI(貪欲法)** に切り替えて継続する。
4. 詰み(どうしても動けない)と証明された場合は停止してメッセージを出す。

対応ルール: **draw-1・ストック無制限リサイクル**(この前提がソルバーの状態縮約の妥当性を支える。詳細は §4.1)。

## 2. アーキテクチャ

| レイヤ | ファイル | 責務 |
|---|---|---|
| ルール層 | `game.ts` | 合法手生成(`findLegalMoves`)、移動検証(`moveCards`)、ドロー(`flipFromStock`)、勝利判定(`checkWin`)。純粋関数のみ |
| AI層 | `engine.ts` | 簡易AI(`planNextAction`)、詰み判定(`isDeadlocked`)、完全探索ソルバー(`createSolver`/`solveSync`)、プラン圧縮(`compactPlan`)、プラン展開(`expandPlan`) |
| UI層 | `Board.tsx` | フェーズ機械、タイマ駆動、キャンセル処理、ステータス表示 |

AI層・ルール層は React に依存しない純関数群であり、すべての状態遷移は「旧状態 → 新状態」のイミュータブルな生成で行われる。

### 基礎型

```ts
type Action = { kind: 'move'; move: Move } | { kind: 'draw' };
```

- `move`: `Move { sourceType, sourceIndex, targetType, targetIndex, cardCount }` の実行。`applyAction` は内部で `moveCards` を呼び、不正なら `null` を返す。
- `draw`: `flipFromStock` の実行。ストック空ならウェイストを反転してリサイクルする。

### ループ防止キー(`serializeState`)

盤面全体(ストック/ウェイスト/基礎/場札の各カード id と表裏)を一意な文字列に直したものをキーとし、一度訪れた盤面を記憶して再訪を禁止する。簡易AIはこの集合で無限ループを回避する。

## 3. フェーズ遷移(Board.tsx)

```
            ┌──────────────────────────────────────────────┐
            │                                              │
  ▶自動 ──► │ idle ──► solving ──won──► replaying ──┐      │
            │   ▲         │                         ▼      │
            │   │         ├─unsolvable─► idle(メッセージ)   │
            │   │         └─budget────► greedy ◄─────────┘   │
            │   │                                            │
            │   └──── 手動操作 / 停止ボタンで強制 idle ◄─────┘
            └──────────────────────────────────────────────┘
```

| フェーズ | 意味 | ボタン表示 |
|---|---|---|
| `idle` | 停止中(手動操作可能) | ▶ 自動 |
| `solving` | ソルバー解析中 | ⏹ 解析停止 |
| `replaying` | 勝利プランの再生中 | ⏸ 停止 |
| `greedy` | 簡易AIによる継続中 | ⏸ 停止 |

オートモード中(`phase !== 'idle'`)は `.auto-mode` CSS クラスにより場のポインタ操作が無効化される。

### 定数

| 定数 | 値 | 意味 |
|---|---|---|
| `SOLVE_TICK_MS` | 30 | 解析の刻み(ms)。30ms ごとに 2 万ノードずつ消化 |
| `SOLVE_SLICE_NODES` | 20000 | 1 tick 当たりの探索ノード数 |
| `SOLVE_MAX_NODES` | 150000 | 解析の総ノード上限(≈ 数秒) |
| `REPLAY_TICK_MS` | 16 | 再生/簡易AIの実行間隔(最高速固定・約60fps)。**速度調整機能は削除済み** |

## 4. 完全探索ソルバー(engine.ts)

### 4.1 理論的背景: 状態縮約

draw-1・無制限リサイクルのルールでは、**ストック+ウェイストは自由回転可能な循環集合**である。すなわち:

- 何度でもドローを繰り返せるため、サイクル内の任意のカードを**任意のタイミングでウェイスト上面に取り出せる**(コストはドロー回数のみ)。
- 取り出し順序は解の存在に影響しない。**並び順ではなく「残っているカードの集合」だけが意味を持つ**。

そこで探索状態を次のように縮約する:

```ts
interface SolState {
  cycle: string[];        // ストック+ウェイストのカードidのソート済み配列(= 集合)
  order: string[];        // 同じ残カードだが「次にドローされる位置を先頭とした循環の実順序」
  foundations: Card[][];  // 4 山
  tableau: Card[][];      // 7 列(表裏フラグ付き)
}
```

これにより状態空間が劇的に縮小され、メモ化DFSによる完全探索が実用時間で成立する。

`order` は実際のゲームのドロー順を再現したもの。draw-1 では「stock の上面から底面 → waste の底面から上面」の順でカードがめくられ、リサイクル後も同一の周回順序が繰り返される。したがって循環の実順序は `reverse(stock) ++ waste` と表せ、`order[0]` が次にウェイスト上面へ出るカードを指す。

- `cycle`(集合)はメモ化ハッシュキー(`hashKey`)の算出に使う。**キーには `order` を含めない**。ポインタ位置・実順序は解の存在に影響しないため、キーを集合ベースに保つことで状態縮約(メモ再利用率)の効果が失われない。
- `order` は候補手の**生成順序**(§4.4)と、extract 後のポインタ進行(§4.2)にのみ使う。

> 注意: この縮約は draw-3 では成立しない(1回のドローで3枚が組になり順序が意味を持つため)。

### 4.2 探索ステップ(`PlanStep`)

```ts
type PlanStep =
  | { kind: 'extract'; cardId; targetType: 'foundation' | 'tableau'; targetIndex }
  | { kind: 'move'; move: Move };
```

- `extract`: サイクル内のカード `cardId` を取り出して基礎/場に置く(縮約モデル上はドロー不要の即時操作)。`applyPlanStep` では取り出したカードの**直後のカードが新しい `order[0]`(ポインタ位置)になる**よう `order` を回転・縮小する。
- `move`: 通常の場札/基礎間の移動。`order` は不変。

### 4.3 メモ化DFS

- 反復型DFS(明示的スタック)。フレーム = `{ state, key, cands(候補手), idx }`。
- メモ: `Map<number, 1 | 2>`(1 = 探索中 IN_PROGRESS、2 = 負け LOST)。
  - 子状態がメモ済みなら再探索しない。探索中マークは経路上の循環検出として働く。
  - 全候補が尽きたフレームは LOST として確定し、以後同一キーは即座に棄却される。
- 勝利判定: 4 基礎がすべて 13 枚(`isWonSol`)。子状態生成時に最初にチェックされる。
- ハッシュキー(`hashKey`): 状態文字列(cycle文字 + 基礎枚数 + 場札id/表裏)に対し FNV-1a 変種を2系統計算し `h1 * 2097152 + (h2 >>> 11)` の **53bit 整数キー**に圧縮(JS の Number で正確に表現できる範囲)。文字列キー比でメモリ効率が良い。
- ノード数 = 展開した子状態数。`maxNodes` 到達で `budget` 停止。

### 4.4 候補手の生成順序(`solCandidates`)

分岐順序は**解の発見速度**にのみ影響し(全分岐を最終的に試すため)完全性には影響しない。現在の優先順:

| 順 | カテゴリ | 内容 |
|---|---|---|
| 1 | 安全な基礎送り | 場札上面→基礎、cycle→基礎 のうち §5.2 の安全条件を満たすもの。ランク昇順 |
| 2 | 裏向き公開 | 表向き run 全体を別列へ移動し裏カードをめくる t→t |
| 3 | King取出し | cycle 内の K → 空き列 |
| 4 | その他の取出し | cycle 内カード → 場(空き列以外/非K) |
| 5 | その他の t→t | run の部分分割(k < run)、全run→空でない列 への移動など |
| 6 | 危険な基礎送り | 安全条件を満たさない基礎送り。ランク昇順 |
| 7 | 基礎からの引き戻し | f→t(詰み回避の一時退避に必要) |

除外されている枝:
- **空きベース間のKing-run移動**(全て表向きの列から空き列への全run移動)——列は互換的であり構造的に同型のシャッフルなので探索しない(解の存在に影響しないことを含めて検証済み)。

#### 分岐順序とドローコスト(order 導入)

クリアまでの手数(= 移動 + ドロー)のうち、ドロー総量は「プラン内 extract の実行順序と循環回転との位相」で決まる。extract 1件の実際のコストはポインタから当該カードまでの巡回距離であり、順序が回転と無関係だと1件あたり最大サイクル1周分のドローが発生する。

そこで `cycle` 内カードの列挙をソート済み集合ではなく **`order`(現在のドロー位置起点)** で行う:

- カテゴリ3・4(cycle→場の取出し)は `order` 順そのもの = **ポインタからの距離昇順**で候補生成される。
- カテゴリ1(cycle→基礎)も `order` 順に列挙した後、ランク昇順の安定ソートを通すため、実効順は「ランク昇順、同ランク内は距離昇順」となる。
- これにより DFS が最初に見つける解の extract 順序が概ね回転方向に沿い、`expandPlan` 再生時のドロー連鎖が大幅に削減される。
- 候補の**並べ替えのみ**であり分岐集合は不変。完全性・メモ化効率(`hashKey` は集合ベース)には影響しない。
- 距離昇順は貪欲な近傍選択であり、ドロー総量の大域最適(巡回経路問題)ではない。

### 4.5 API

```ts
createSolver(state, maxNodes): SolverHandle  // 再開可能なソルバー生成
  .step(sliceNodes): { status: 'running'|'won'|'unsolvable'|'budget', nodes }
  .getPlan(): PlanStep[] | null              // won 時の勝利手順
solveSync(state, maxNodes): { status, plan, nodes }  // 同期一括版(テスト用)
```

決定的(deterministic): 同一入力・同一上限なら常に同一結果。

### 4.6 プラン展開(`expandPlan`)

縮約モデルの手順 `PlanStep[]` を実際の `Action[]` へ変換する:

- `extract` の場合: 実際には `flipFromStock` を繰り返して当該カードがウェイスト上面に来るまでドローし(ガード128回)、その後 `waste → 目的地` の move を発行する。
- `move` の場合: そのまま `moveCards` を発行する。
- **途中で移動が失敗した場合、それまでに成功した Action のみを返して打ち切る**(部分返却)。呼び出し側は再生完了時に必ず勝利判定を行うため、異常時はフェーズが idle に戻りメッセージが出る。

### 4.7 プラン圧縮(`compactPlan`)

ソルバーが返すのは「最初に見つかった解」であり最短性は保証されない。そこで展開前に、縮約モデル上で手順を事前シミュレートし**プラン内ループ(同一盤面への往復)を除去**する。

- `plan` を `applyPlanStep` で逐次適用し、各ステップ後の盤面ハッシュキー(`hashKey`)と「その時点でのステップ数」を記録する。
- あるステップ後のキーが過去のプレフィックス m と一致したら、m 以降に当たる区間(同一盤面へ戻るループ)を切り捨てて継続する。
- 同一状態へ戻る手順のみを除去するため勝利性は保たれ、ステップ数は単調に減少する。
- `applyPlanStep` が失敗した場合(正常なプランでは発生しない)は残りを無圧縮で返す fail-safe 構成。

UI は `won` 判定時に `expandPlan(現在盤面, compactPlan(現在盤面, plan))` の順で呼び出す(§7.2)。圧縮は PlanStep レベルの操作であり、ドロー展開後の Action 列に対して行っても意味が薄れるため、必ず展開前に適用する。

## 5. 簡易AI(`planNextAction`)

ソルバーが予算内で解を出せなかった場合のフォールバック、およびヒント表示の基盤。1手ずつその場で最良の手を選ぶ貪欲法。訪問済み集合(`visited`)により同じ盤面への再訪を禁止し、ループを構造的に防止する。

### 5.1 手の優先度

以下の順で連結した候補列の先頭から、「適用成功・自己ループでない・未訪問」の最初の手を採用する。

| 優先度 | カテゴリ | 関数 | 内容 |
|---|---|---|---|
| 1 | 安全な基礎送り | `safeFoundationActions` | §5.2 の条件を満たす送り。ランク昇順(A,2 を最優先) |
| 2 | 裏向き公開 | `revealingActions` | 表run全体を移動して裏カードをめくる手 |
| 3 | ウェイスト→場 | `wasteToTableauActions` | ウェイスト上面の場への配置 |
| 4 | 露出作り | `exposureActions` | run を部分分割し、新たに露出するカードが他カードの受け皿になる手 |
| 5 | 危険な基礎送り | `unsafeFoundationActions` | 安全条件を満たさない送り。ランク昇順 |
| 6 | ドロー | (固定) | `flipFromStock` |
| 7 | 有用シャッフル | `usefulShuffleActions` | 上記以外の合法 t→t のうち、適用後にカテゴリ1〜4の手が新たに生まれるもの |

どれも適用できない場合は `null` を返し、UI 側は停止メッセージを表示する。

設計メモ:
- 「危険な基礎送り」をドローより先に置くのは、基礎送りが単調(後戻りなし)でループを生まないため。
- かつて存在した「空き列作成」カテゴリ(全て表向きの列→空き列)は、**常に構造同型の無意味なシャッフルであることが判明したため削除**した。真の空き列活用はカテゴリ2(裏向き公開)とソルバーの King取出し(§4.4-3)が担う。

### 5.2 安全な基礎送りの条件(Rule of 2)

`isSafeFoundationSendAgainst(card, foundations, suits)`:

- ランク ≤ 2(A, 2)→ **常に安全**(A は場で何の受け皿にもならず、2 の受け皿は A のみ)。
- ランク ≥ 3 → **両対色の (r−1) が両方とも基礎に置かれている場合のみ安全**。
  - 例: 赤6 は 黒5♠・黒5♣ が両方基礎に上がっていれば安全。
  - 根拠: 対色 (r−1) が場に残存する限り、赤 r は黒 (r−1) の受け皿として必要になり得るため。

この条件は簡易AIの優先度分類と、ソルバーの分岐順序(§4.4)の両方で使われる。なお「より弱い条件(対色最小値 + 2)」を**強制適用**すると解けなくなるケースがあることを実測で確認しており、強制は行わない(ソルバーではあくまで順序付けにのみ使用)。

## 6. 詰み判定(`isDeadlocked`)

「これ以上どんな操作をしても局面が進まない」ことの厳密判定。

1. `productiveMoves` = 合法手のうち**基礎をソースとしないもの**(場→基礎、場→場、ウェイスト→場、ドロー後の配置など)。1手でもあれば詰みではない。
2. 現在のウェイスト上面で productive がなければ、**ストック↔ウェイストの循環を1周分シミュレート**(リサイクル反転を含む)し、各ドロー段階のウェイスト上面ごとに productive を再評価する。
3. 循環全体のどこにも productive がなければ `true`(詰み)。

UI は常時この判定を監視し、`true` になったらゲームオーバー(詰み)オーバーレイを表示する。オートモード中も同様に停止条件となる。

## 7. UI統合の動作仕様(Board.tsx)

### 7.1 開始

「▶ 自動」クリック時(`won` でも `isGameOver` でもない場合):

1. ヒント表示をクリア、ステータスをクリア、ノード表示をリセット。
2. `createSolver(現在盤面, SOLVE_MAX_NODES)` を生成し `solving` へ。

### 7.2 solving(30ms 周期)

- `solver.step(SOLVE_SLICE_NODES)` を実行し、ノード数を「最善手を解析中… (Nノード)」に表示。
- `running` → 継続。
- `won` → `compactPlan(現在盤面, plan)` でループを除去してから `expandPlan(現在盤面, …)` で Action 列を組み、`replaying` へ。
- `unsolvable` → idle へ戻り、「この配布は自動プレイではクリアできません」を表示。
- `budget` → 訪問済み集合を現在盤面のみで初期化し、「解析上限に達したため簡易AIで継続します」を表示して `greedy` へ。

### 7.3 replaying / greedy(16ms 周期・最高速固定)

共通の停止条件: `won` または `isDeadlocked` 成立 → idle へ。

- **replaying**: キューから 1 Action/tick ずつ取り出して適用。キュー枯渇で idle。適用失敗時は「再生中に問題が発生したため停止しました」。
- **greedy**: `planNextAction(現在盤面, visited)` で 1 手ずつ選択・適用し、適用後の盤面を visited に追加。手が見つからなければ「有効な手が見つからないため自動プレイを停止しました」。

### 7.4 キャンセル

| 操作 | 動作 |
|---|---|
| オートボタン再クリック(⏹/⏸) | 即時中断(idle 化、ソルバー・キュー破棄) |
| オート中のストッククリック | 中断(「手動操作により自動プレイを中断しました」) |
| オート中のカード操作(ダブルクリック等) | 同上 |
| オート中のドラッグ開始 | そもそも開始不可(`phase !== 'idle'` で拒否) |
| 「新しいゲーム」 | 全状態(visited・ソルバー・キュー・フェーズ)をリセット |

## 8. 既知の制限・特性

- **予算超過の末尾集団**: ランダム配布の一部(実測でおよそ 3 割)は 150k ノードでは勝利証明も不可能証明もできず、簡易AIにフォールバックする。このうち簡易AIで完走できるのは一部(実測 2〜3 割程度)であり、**理論的に解ける配布でも自動でクリアできない場合がある**。上限を上げれば解決率は上がるが、所要時間が比例して増える(≈0.035ms/ノード)。
- **解けない配布の存在**: Klondike はランダム配布の 1〜2 割程度がそもそも解なし。ソルバーは予算内で証明できれば `unsolvable` を返す。
- **expandPlan の部分返却**: §4.6 の通り、展開失敗時は打ち切られる(実運用で発生は確認されていない)。
- **プランの最短性は非保証**: ソルバーは最初に見つかった解を返す。`compactPlan`(§4.7)によるループ除去と、`order` 距離順の分岐付け(§4.4)によりクリアまでの手数(移動+ドロー)は大幅に削減されるが、大域的な最小手数保証はない(extract 順序の距離昇順も貪欲な近傍選択にとどまる)。
- **ルール依存**: 状態縮約は draw-1・無制限リサイクル専用。draw-3 等への rule 変更時はソルバーの再設計が必要。

## 9. 検証結果(参考)

> 本節の数値は、`order`(循環実順序)導入および `compactPlan` 追加**前**の旧実装での計測値である。分岐順序の変更により同程度の傾向が維持される想定だが、手数・ノード数の正確な統計は要再計測。

シード付き 100 配布 × 150k ノードの E2E 検証(`mulberry32(i*7919+1)`):

| 項目 | 結果 |
|---|---|
| 自動クリア(ソルバー) | 69% |
| 不可能証明 | 0% |
| 予算超過(簡易AIへ) | 31%(うち簡易AI完走 2%) |
| 解けた配布の平均ノード数 | ≈12,800 |
| リプレイ合法性・保存則(52枚不変)・決定性 | 全件合格 |

単体テスト: 安全基礎送りの優先適用 / 詰み状態 ⇒ `unsolvable` 証明 / 構築状態での詰み判定、いずれも合格。

## 10. 配布生成フィルタ(`dealSolvableState`)

ランダム配布には理論上勝ち不可のものが含まれるため、**新規ゲーム開始時に完全ソルバで解の存在を検証し、証明可能な配布だけを採用する**フィルタ。`engine.ts` に実装され、`Board.tsx` の初期状態生成と「新しいゲーム」の両方で使用する。

```ts
dealSolvableState(options?: { difficulty?: DealDifficulty; rng?: () => number }): DealtGame
// DealtGame { state, attempts, proven }
// DealDifficulty = 'easy' | 'normal' | 'hard'(localStorage に永続化され UI で選択可能)
```

### 採用ポリシー

各試行で `dealCards` → `solveSync(state, budget)` を実行し、ステータスごとに:

| ステータス | 動作 |
|---|---|
| `won` | **採用候補**(`proven: true`)。勝利プランまで検証済み |
| `unsolvable` | **棄却して再抽選**。絶対解けない配布は出荷されない |
| `budget` | 未証明。フォールバックとして保持し、証明済み候補が最終的に無ければ返す(`proven: false`) |

### 難易度パラメータと特性

| 難易度 | budget | 候補数 | 戦略 |
|---|---|---|---|
| easy | 5,000 | 8 | 最初の `won` を即採用(小予算で解ける=確実に易しい) |
| normal | 40,000 | 1 | 従来動作(初回候補を評価) |
| hard | 80,000 | 3 | 複数候補を解き**ノード数最大**(= 最も難しい)の証明済み配布を選ぶ。ノード数が予算の 75% 以上なら早期確定 |

- normal の `budget = 40000`: 棄却コスト(フル探索消費)と証明率のトレードオフからの選定。実測(シード 30 配布)で平均生成時間 ≈1.1 秒。
- hard の所要時間: 実測 0.1〜4.2 秒(seed 3 件)。全候補が `budget`/`unsolvable` の場合は最大 ≈8 秒。
- **難易度バイアス**: normal/easy は証明に多くのノードを要する「難敵」が棄却されるため母集団より易しく偏る(解ける保証は厳密なまま)。hard は逆方向のバイアスで、証明済みの中でも特に難しい配布を提供する。
- **ロード表示**: 生成は `dealWorker.ts`(Web Worker)内で非同期実行され、UI スレッドはブロックされない。`Board.tsx` は `isDealing` 状態のロードオーバーレイ(スピナー + 「配布を生成中…」)を表示し、Worker の応答で盤面を確定する。Worker 生成に失敗した環境では同期版 `dealSolvableState` にフォールバックする。生成中はタイマ停止・詰み判定スキップ・全操作無効(オーバーレイが全面を覆う)。

## 11. ルール設定とシード(`GameRules` / デイリー)

### GameRules(types.ts)

```ts
interface GameRules {
  drawCount: 1 | 3;        // ストックからめくる枚数
  maxRecycles: number;     // リサイクル上限(-1 = 無制限)
  scoring: 'standard' | 'vegas';
}
```

- `GameState.rules` / `GameState.recycles` として盤面に保持されるため、セーブ&再開・アンドゥで一貫性が保たれる。⚙️設定モーダルで変更し、localStorage(`solitaire-rules`)に永続化。適用は次の「新しいゲーム」開始時(配布自体はルール非依存なので同じシードでどのルールでも同じ並びになる)。

### ソルバー/自動プレイとの互換性

完全ソルバ・簡易AI・詰み検出(`isDeadlocked`)は **draw-1 + 無制限リサイクル** を前提に設計されている。したがって:

| ルール | 自動プレイ | ヒント | 詰み判定 |
|---|---|---|---|
| draw-1 & 無制限 | ✅ | ✅ | ✅ |
| draw-3 または リサイクル制限 | ❌ ボタン無効化 | ❌ ボタン無効化 | ❌ スキップ(誤検出防止) |

- 配布生成フィルタ(§10)自体は全ルールで有効(draw-1/無制限前提の証明だが、手動プレイの「初期盤面が悪くない」フィルタとして機能)。リサイクル制限時は証明の厳密性は失われる点に注意。

### スコア方式

- `standard`: waste→場 +5、→基礎 +10、めくり +5、基礎→場 −15
- `vegas`: 基礎送りのみ +5(それ以外は加算しない)

### シードとデイリーチャレンジ

- `mulberry32(seed)`(game.ts)により決定論的なシャッフルを実現。`dealSolvableState({ seed })` は同一シードなら常に同一の証明済み配布を返す(棄却ループも含めて再現可能)。
- **デイリー**: 📅ボタン → シード = ローカル日付の YYYYMMDD・難易度 normal 固定。達成済みフラグを localStorage(`solitaire-daily-YYYY-MM-DD`)に記録し、ボタンに ✓ 表示。
- **シード共有**: ⚙️設定モーダルの「シードで開始」で任意の正整数シードを再現できる。勝利モーダルにも使用シードを表示。
- 中断セーブにも `seed` / `daily` を保存し、再開後の勝利でもデイリー達成が正しく記録される。
